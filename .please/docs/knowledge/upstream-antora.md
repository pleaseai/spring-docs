# Upstream Antora Pipeline — How Spring Boot Docs Are Actually Built

> Field notes from probing `spring-projects/spring-boot` v4.1.1. These facts drive
> `scripts/fetch-upstream.ts` and `scripts/convert.ts`. Verified 2026-09-11.

## Why we do not write conversion rules by hand

A hand-written AsciiDoc→Markdown converter would have to reimplement Spring's own
Antora extensions. Measured across the 227 `.adoc` files in Spring Boot 4.1.1:

| Construct | Occurrences | Who resolves it |
|---|---|---|
| `javadoc:FQN[]` | 3,056 | `@springio/asciidoctor-extensions/javadoc-extension` |
| `xref:module:path.adoc#frag[]` | 2,836 | Antora content-classifier |
| `configprop:name[]` | 423 | `@springio/asciidoctor-extensions/configuration-properties-extension` |
| `include-code::Name[]` | 326 | `@springio/asciidoctor-extensions` (index) |
| `[configprops,yaml]`, `[tabs]` | 288 | springio extensions (tabs stay as AST — see below) |

`include-code::` resolution is non-obvious: the target path comes from the **enclosing
section's anchor id**, not the page path. On page `reference/pages/data/nosql.adoc`
inside section `[[data.nosql.redis.connecting]]`, `include-code::MyBean[]` resolves to
`ROOT:example$java/org/springframework/boot/docs/data/nosql/redis/connecting/MyBean.java`
plus the matching `.kt`, emitted as a Java/Kotlin tab pair.

## Where the docs live (4.x layout)

The 4.x tree differs from 3.x — there is no `spring-boot-project/spring-boot-docs`.

```
documentation/spring-boot-docs/src/docs/antora/    <- component root (antora.yml, nav.adoc)
  modules/{ROOT,reference,how-to,tutorial,appendix,specification,cli,build-tool-plugin,api}/
```

Module page counts at v4.1.1, measured over the merged tree the converter actually sees
(git checkout + content archives): appendix 103, reference 89, how-to 28, specification 11,
ROOT 7, build-tool-plugin 3, cli 3, tutorial 2 — 246 pages, matching the corpus total used
throughout this file. `api` ships no `pages/` at all.

`appendix` dominates that total because almost all of it is generated rather than
authored: `auto-configuration-classes/` alone is 96 pages, and the configuration-property
tables are the rest. Those arrive with `root-aggregate-content`, so counting the git
checkout before the archive merge gives a much smaller appendix — and a corpus that does
not add up to 246.

## The decisive fact: content zips are published to Maven Central

> **Caveat measured on 2026-09-11**: only for some versions. `spring-boot-docs` exists on
> Maven Central for 2.2.9-2.4.2 and then from 4.0.8 (plus 4.2.0-M1). 4.0.0-4.0.7 and 4.1.0
> have no archive, so they cannot be built. Check
> `https://repo1.maven.org/maven2/org/springframework/boot/spring-boot-docs/maven-metadata.xml`
> before assuming a version is buildable.

Spring Boot's `antora.yml` carries almost no attributes — they are generated by Gradle
(`buildSrc/.../AntoraAsciidocAttributes.java`) from the dependency BOM, and the Java/Kotlin
sample sources are copied into `ROOT:example$` by the build. That would normally force us
to run a full Gradle build of Spring Boot.

It does not, because those build outputs are published as ordinary Maven artifacts:

```
https://repo1.maven.org/maven2/org/springframework/boot/spring-boot-docs/<version>/
  spring-boot-docs-<version>-root-aggregate-content.zip               (1.3 MB, 2024 files)
  spring-boot-docs-<version>-actuator-rest-api-aggregate-content.zip
  spring-boot-docs-<version>-api-catalog-content.zip
  spring-boot-docs-<version>-{gradle,maven}-plugin-catalog-content.zip
  spring-boot-docs-<version>-maven-plugin-aggregate-content.zip
```

`root-aggregate-content.zip` contains `modules/antora.yml` — a full component descriptor
carrying **912 resolved asciidoc attributes** (`version-spring-boot: 4.1.1`,
`github-ref: v4.1.1`, `url-spring-framework-docs`, `include-java`, every `version-*` from
the BOM) — plus `modules/ROOT/examples/{java,kotlin}/**` and the generated appendix partials.

Zip entries are timestamped `1980-02-01`, so the archives are byte-stable across downloads.

**Consequence**: `(project, version) → docs` needs only a sparse git checkout of the
component root plus an HTTP fetch of these zips. No JVM, no Gradle, no `zip_contents_collector`.

## Toolchain compatibility (verified under Bun 1.3.14)

- `@asciidoctor/core@4.x` is a native-JS rewrite and runs under Bun, but the springio
  extensions still use the Opal API (`registry.$groups().$store`), so they need `2.2.x`.
- `@asciidoctor/core@2.2.8` (Opal) **does** run under Bun. Antora 3.2 pins `~2.2`, so one
  version satisfies both.
- `@asciidoctor/tabs` requires a global `Opal`, so it must be required *after* Asciidoctor.
  Antora's own loader does this; do not require it directly.

## Antora as a library (the path we use)

Do not shell out to the `antora` CLI — it only emits an HTML site and needs a UI bundle.
Drive the pipeline modules directly:

```js
const playbook = buildPlaybook(['--playbook', file], {}, undefined)  // @antora/playbook-builder
const asciidocConfig = resolveConfig(playbook)                       // @antora/asciidoc-loader
const catalog = classifyContent(playbook, await aggregateContent(playbook), asciidocConfig)
for (const page of catalog.getPages((p) => p.out)) {
  const cv = catalog.getComponentVersion(page.src.component, page.src.version)
  const doc = loadAsciiDoc(page, catalog, cv.asciidoc)   // <- Asciidoctor Document, fully resolved
}
```

Three traps, all hit during the probe:

1. `config.extensions` must hold **required module objects**, not strings. Get the config
   from `resolveConfig(playbook)`; passing `playbook.asciidoc` raw fails with
   `ext.register is not a function`.
2. Pass **`componentVersion.asciidoc`**, not `playbook.asciidoc`, to `loadAsciiDoc`.
   The component descriptor's attributes live only on the component version; without them
   `include-code::` logs `no search locations defined` and silently resolves nothing.
3. A local content source **must be a git worktree**, or the aggregator fails with
   `Local content source must be a git repository: <dir>`. It finds one by walking up the
   directory tree, so a fetched tree sitting inside an unrelated repository appears to work
   and the same tree elsewhere does not. `fetch-upstream.ts` therefore runs
   `git init && git add -A && git commit` on its output, making the source self-contained.
   The playbook declares that directory with `branches: HEAD`; Antora then reads the
   worktree, so files written after the commit (the playbook itself) are still picked up.

## Shape of the AST we convert

- Blocks come back as a normal Asciidoctor AST (`getBlocks()`, `getContext()`, `getStyle()`).
  Tab groups appear as `context: example, style: tabs`.
- Inline content is **not** an AST: `block.getContent()` returns a restricted HTML string
  (`<a>`, `<code>`, `<strong>`, `<em>`, `<sub>`, `<sup>`, `<br>`). Inline conversion is
  therefore a small HTML→Markdown pass, not an AST walk.
- Antora resolves `xref:` targets to `.html` URLs; the converter rewrites them to `.md`.

## Converter specification (measured over all 246 pages of Boot 4.1.1)

### Do not register `@asciidoctor/tabs`

Upstream registers it because it targets HTML. It rewrites every `[tabs]` block into
per-panel HTML passthrough blocks — 2,364 `pass` nodes across the corpus, each containing
`<div class="tabpanel">`. That destroys the structure we need. With the extension omitted,
tab groups survive as `example:tabs` AST nodes (288 of them) wrapping a `dlist` of
`Maven::` / `Gradle::` / `Java::` / `Kotlin::` entries — exactly the shape
`product-guidelines.md` wants emitted as headed code fences.

The other four springio extensions **are** registered: they resolve macros into ordinary
AsciiDoc, not HTML.

| Tag | Count | Markdown |
|---|---|---|
| `<a class="xref page" href="…">` | 8,400 | `[text](path.md#frag)` — rewrite `.html` → `.md` |
| `<code>` | 7,713 | `` `text` `` |

xref hrefs are already **relative** to the current page (`../installing.html#anchor`), so
only the extension is rewritten — never the path.

### Two walker traps

Both were hit while probing; the second is silent.

1. **`dlist.getBlocks()` returns `[terms, description]` pairs, not nodes.** Walking them as
   nodes throws `node.getContext is not a function`. Use `getItems()` for `dlist` and skip
   `getBlocks()` entirely.
2. **`admonition.getContent()` flattens nested blocks to HTML.** A compound admonition
   containing a code block yields `<div class="listingblock">…</div>`. Check
   `getContentModel() === 'compound'` and recurse into `getBlocks()` instead; use
   `getContent()` only for the simple case.

Read `listing` bodies with `getSource()`, not `getContent()` — the latter carries the
code-folding extension's `<span class="fold-block">` wrappers.
