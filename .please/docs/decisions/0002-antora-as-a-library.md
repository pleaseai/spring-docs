# ADR-0002: Drive Antora as a Library and Emit Markdown from the Asciidoctor AST

## Status

Accepted — 2026-09-11

## Context

`ARCHITECTURE.md` names `scripts/lib/antora-rules.ts` as the home of "centralized conversion
rules (xref, include, admonitions, tab blocks, attribute substitution)", and
`tech-stack.md` deferred the parser choice: "Conversion implementation may use a library
(e.g., Asciidoctor.js) for parsing, then a custom Markdown emitter — or a direct AST-walking
converter. Decision deferred to the implementation track."

The first prototype track measured what "write the rules ourselves" actually costs. Across
the 227 `.adoc` files of Spring Boot 4.1.1 (see
`.please/docs/knowledge/upstream-antora.md` for the full survey):

| Construct | Occurrences |
|---|---|
| `javadoc:FQN[]` | 3,056 |
| `xref:module:path.adoc#frag[]` | 2,836 |
| `configprop:name[]` | 423 |
| `include-code::Name[]` | 326 |
| `[configprops,yaml]` / `[tabs]` | 288 |

None of these are stock AsciiDoc. They are Antora module coordinates and Spring's own
Asciidoctor extensions, and their semantics are non-obvious — `include-code::MyBean[]`
resolves through the *enclosing section's anchor id*, not the page path, and expands to a
Java/Kotlin tab pair. Reimplementing them means shadowing `spring-io/antora-extensions` and
tracking its changes forever, in a repo whose first content invariant is "meaning is
preserved" and whose second is "no silent fallbacks".

Two facts, both verified during the prototype, make delegating to the real toolchain viable:

1. **The generated inputs are published.** Spring Boot's asciidoc attributes are generated by
   Gradle from the dependency BOM, and the Java/Kotlin samples are copied in by the build —
   but those outputs ship to Maven Central as `spring-boot-docs-<version>-*-content.zip`.
   `root-aggregate-content.zip` carries a component descriptor with 912 resolved attributes
   and the full `ROOT:example$` tree. We need no JVM and no Gradle.
2. **The toolchain runs under Bun.** The springio extensions still use the Opal extension API,
   so they require `@asciidoctor/core@~2.2` rather than the 4.x native rewrite. Antora 3.2
   pins `~2.2`, so one version satisfies both, and `2.2.8` was confirmed working under
   Bun 1.3.14.

## Decision

1. **Use Antora's pipeline modules as a library**, not the `antora` CLI. `scripts/convert.ts`
   calls `@antora/playbook-builder` → `@antora/content-aggregator` →
   `@antora/content-classifier` → `@antora/asciidoc-loader` to obtain a fully resolved
   Asciidoctor `Document` per page. The CLI is rejected because it only emits an HTML site
   and requires a UI bundle.

2. **Register Spring's own extensions** rather than reimplementing them:
   `@springio/asciidoctor-extensions` and its `javadoc-extension`,
   `configuration-properties-extension`, and `section-ids-extension` — the set
   `buildSrc/.../Extensions.java` configures upstream, minus `@asciidoctor/tabs`.
   Upstream registers `@asciidoctor/tabs` because it renders HTML; it rewrites tab groups
   into HTML passthrough blocks, which would destroy the `example:tabs` AST structure this
   pipeline needs to keep, so it is left unregistered and not depended on at all.

3. **Emit Markdown from the AST with our own converter**, in two pure modules:
   - `scripts/lib/markdown-converter.ts` — walks the block AST (`getBlocks()` /
     `getContext()` / `getStyle()`).
   - `scripts/lib/inline-html.ts` — converts the restricted inline HTML that
     `block.getContent()` returns (`<a>`, `<code>`, `<strong>`, `<em>`, `<sub>`, `<sup>`,
     `<br>`) to Markdown, rewriting Antora's resolved `.html` xref targets to `.md`.

   Both are pure functions and perform no I/O, preserving the ARCHITECTURE invariant
   "conversion rules are pure". `antora-rules.ts` as named in ARCHITECTURE.md is superseded
   by these two modules.

4. **`fetch-upstream.ts` acquires two inputs**: a sparse git checkout of the component root
   at the release tag, and the published content zips from Maven Central, merged into one
   Antora content source. The merged tree is committed as its own git repository, because
   Antora's aggregator accepts a local content source only if it is a git worktree.

5. **Accept the runtime dependencies** this requires, as the ADR-gated exception the
   ARCHITECTURE invariant calls for: `@antora/*` (playbook-builder, content-aggregator,
   content-classifier, asciidoc-loader), `@asciidoctor/core@~2.2`, and
   `@springio/asciidoctor-extensions`.

## Consequences

### Positive

- **Fidelity by construction.** `xref:`, `include::`, `include-code::`, `javadoc:`,
  `configprop:`, and tab blocks are resolved by the same code that produces docs.spring.io.
  We cannot silently diverge from upstream semantics on constructs we never implemented.
- **The conversion surface shrinks to what is genuinely ours**: block AST → Markdown, and
  inline HTML → Markdown. Roughly 20 block types instead of an AsciiDoc dialect.
- **Deterministic inputs.** Zip entries are timestamped `1980-02-01` and the git ref is a
  tag, so the same `(project, version)` fetches byte-identical inputs.
- **No JVM in CI**, preserving the "no Spring runtime, no JVM in CI for content builds"
  architecture boundary.
- **Upstream extension fixes arrive as dependency bumps**, not as reverse-engineering work.

### Negative

- **Buildable versions are whatever Spring chose to publish.** The pipeline needs the
  `spring-boot-docs` content archive, and Maven Central has it for 2.2.x-2.4.2 and then
  only from 4.0.8 — 4.0.0-4.0.7 and 4.1.0 are tagged but unbuildable. Measured after the
  fact, not anticipated: the original assumption was that a supported *range* existed.
  Detection now verifies archive availability per version instead of trusting a floor.

- **Dependency surface grows** from "Bun + a parser" to ~8 direct packages and their
  transitive trees. This is the cost the ADR exception exists to authorize.
- **Pinned to `@asciidoctor/core@~2.2` (Opal-based)** until `spring-io/antora-extensions`
  migrates to the 4.x native API. We cannot adopt Asciidoctor 4 unilaterally.
- **Coupled to two Antora internals** that are not part of a documented public API:
  `resolveConfig()` must supply `asciidoc.extensions` as required module objects, and
  `loadAsciiDoc` must receive `componentVersion.asciidoc` rather than `playbook.asciidoc`.
  Both are load-bearing — getting either wrong fails loudly in the first case and *silently
  drops every `include-code::`* in the second. Integration tests must assert on resolved
  sample code, not just on page count.
- **Depends on Spring publishing content zips.** If a project in our coverage window does not
  publish them, that project needs a different acquisition path before it can be onboarded.

### Neutral

- Antora emits page-level warnings for xrefs into components we do not build
  (`gradle-plugin`, `maven-plugin`, `api`). These are configured via the xref extension's
  stub list, and the choice of which components to build is a per-project decision.
- `markdown/` output layout still follows `markdown/<project>/<version>/`, unchanged.
